# Legal Terminus - Project Instructions

## Documentation-First Approach

**CRITICAL: After any feature implementation, always update these files:**

### 1. Epic Stories & Planning Artifacts
- **File:** `_bmad-output/planning-artifacts/epics.md`
- **When:** Any new feature, bug fix, or story completion
- **Update:** 
  - Mark story status (✅ Completed, 🔄 In Progress, ⏳ Not Started)
  - Update acceptance criteria if scope changed
  - Add implementation notes with file paths
  - Update complexity/priority if different than estimated

### 2. Feature Specification
- **File:** `spec.md`
- **When:** User stories, workflows, or API changes
- **Update:**
  - Add/update user story descriptions
  - Document workflow changes
  - Update Firestore schema if modified
  - Add new roles, permissions, or auth methods

### 3. Architecture & Design
- **File:** `_bmad-output/planning-artifacts/architecture.md`
- **When:** Technical decisions, new components, or design patterns
- **Update:**
  - Document new service layer, controller, or API endpoint
  - Add component architecture if UI changed significantly
  - Update database schema diagram if Firestore changed
  - Document any new external integrations

### 4. Implementation Notes
- **File:** `.instructions.md` (this file) or session memory
- **When:** Known issues, decisions, or lessons learned
- **Add:** Brief note about what worked/didn't work

## Common Workflows

### When adding a new Auth method (like we just did):
1. ✅ Implement LoginPage / SignupPage / ForgotPasswordPage components
2. ✅ Update backend auth endpoints and Firebase custom claims
3. ✅ Update `spec.md` → Technology section → Auth methods
4. ✅ Update `epics.md` → E01-S02 story → Acceptance Criteria
5. ✅ Document in architecture.md if flow is complex
6. ✅ Commit with clear message
7. ✅ Create feature branch + PR

### When adding a new Report:
1. ✅ Create backend controller endpoint (`backend/src/controllers/reports.controller.js`)
2. ✅ Create frontend page (`Portal/src/pages/reports/ReportName.tsx`)
3. ✅ Create Firestore indexes if needed (`firestore.indexes.json`)
4. ✅ Update types (`Portal/src/types/task.ts` or new type file)
5. ✅ Update `epics.md` with story completion status
6. ✅ Update `spec.md` if new fields added
7. ✅ Test CSV export if applicable
8. ✅ Commit + create PR

### When fixing a bug:
1. ✅ Identify root cause (update `.instructions.md` or session memory)
2. ✅ Fix code
3. ✅ Update `epics.md` if related story needs status update
4. ✅ Commit with `fix:` prefix
5. ✅ Note in session memory if lesson learned

## Workspace Rules

1. **Every commit must include epic/story status** if work is story-related
2. **No PR without updated spec.md** if requirements changed
3. **All error messages must be user-friendly** (no technical error codes)
4. **TypeScript strict mode** - no `any` types without justification
5. **Feature branches only** - no commits to `main` directly
6. **NEVER hardcode variables** - use environment files or GitHub Secrets:
   - Frontend: `.env.local` (local) + GitHub Secrets (CI/CD)
   - Backend: `.env.qa` (local) + GitHub Secrets (CI/CD)
   - Portal: `.env.local` (local) + GitHub Secrets (CI/CD)
   - **Examples of what to never hardcode:**
     - API keys, tokens, secrets
     - Firebase credentials (use env vars)
     - Database URLs or connection strings
     - Feature flags or feature URLs
     - Admin emails or internal IDs
   - **GitHub Secrets format:** `BACKEND_FIREBASE_PRIVATE_KEY`, `FIREBASE_QA_API_KEY`, etc.
   - **Always include `.env.example`** showing structure (without actual values)
7. **When adding new env variables or GitHub Secrets:**
   - Add to `.env.example` (empty value only)
   - Add to `.env.local` with actual value (for local testing)
   - Add to GitHub Secrets via Settings → Secrets and variables → Actions
   - **Update ALL related workflows** to export the new secret as an env var:
     - `.github/workflows/firebase-preview-qa.yml` (QA deployment)
     - `.github/workflows/firebase-prod.yml` (if exists)
     - Any other CI/CD workflows
